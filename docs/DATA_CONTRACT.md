# Data Contract

**Status:** accepted v1 contract; staged database and application runtime verified

**Prepared:** 2026-08-17

**Accepted:** 2026-08-17

## Purpose

This contract defines the information stored by AI Service Request Automation
before database migrations are written. It keeps 4 kinds of information
separate:

1. the requester's original message;
2. the AI proposal;
3. deterministic validation and human decisions; and
4. the accepted case record delivered to the downstream sandbox.

This separation is the main safety boundary. An AI proposal can be useful even
when it is imperfect because it cannot silently replace the original request or
authorize a consequential action.

## Beginner Mental Model

| Stage | Input | Action | Output | Decision owner |
| --- | --- | --- | --- | --- |
| Intake | Web form or webhook | Store the original request once | Traceable case | Deterministic code |
| AI analysis | Original subject and message | Classify, summarize, extract, and quote evidence | Untrusted proposal | Local AI |
| Validation | Proposal, original text, users, systems, and permissions | Check completeness, exact IDs, access, duplicates, and evidence | Rule results and route | Deterministic code |
| Human step | Reviewable case | Correct, approve, or reject when required | Authorized decision | Service agent or approver |
| Delivery | Accepted case details | Send an idempotent message to the sandbox | Downstream record | Workflow plus downstream API |
| Audit | Every state change | Append an event | Reconstructable history | Application |

## Data Authority

| Data | Authority | May overwrite another layer? |
| --- | --- | --- |
| Original subject and message | Requester or authenticated source | No; stored as received |
| AI proposal | Ollama analysis run | No; retained as evidence |
| User, role, system, and permission reference data | Seeded application records | Yes, only through controlled administration |
| Accepted structured details | Deterministic validation or recorded human correction | Yes, with an audit event |
| Approval decision | Assigned approver | No; a new decision event is recorded |
| Workflow state | Allowed transition rules | Yes, only through an allowed transition |
| Downstream result | Service Desk Sandbox response | No; each attempt is retained |

## Shared Database Conventions

- Primary identifiers use UUIDs generated by the application or PostgreSQL.
- Human-readable references such as `CASE-2026-0001` are separate unique
  columns and are never used as database primary keys.
- Timestamps use `timestamptz` and are stored in UTC.
- Explicit status columns use `varchar` plus `CHECK` constraints so the allowed
  values remain visible in migrations.
- JSONB is reserved for structured payloads that vary by rule or integration.
  Core searchable relationships remain normal columns and foreign keys.
- Passwords and webhook credentials are never stored as plaintext. Only hashes
  or environment-provided secrets are allowed.
- Audit events and delivery attempts are append-only for the application role.
- All seed identities, policies, systems, and requests are fictional.

## Service Desk Sandbox Tables

The sandbox is a separate local service. Its database boundary proves that the
project uses an external API contract instead of writing directly into a fake
downstream table.

### `service_records`

Stores the resulting policy response, incident ticket, approved action, or
authorized status response. `delivery_idempotency_key` is unique so retries
return the existing record instead of creating a duplicate.

### `service_record_events`

Stores append-only sandbox status changes and controlled transient or permanent
failure evidence.

The proposed exact API payload, idempotency behavior, controlled failure
contract, and 2-table schema are defined in
`docs/SERVICE_DESK_SANDBOX.md`. The contract was accepted on 2026-08-17; its
service, 2-table migration, and contract tests passed their user-run disposable
runtime check on PostgreSQL 17.11 on 2026-08-17. This verifies the isolated
sandbox boundary, not primary-application delivery.

## Consequential Identifier Guard

The guard applies to `approver_id`, `case_reference`, and `record_reference`.

1. Preserve the original subject and message.
2. Normalize only surrounding whitespace and letter case; never use fuzzy or
   prefix matching for an identifier.
3. Require the complete proposed identifier to appear in the original text or
   an exact evidence quote.
4. Resolve the identifier against the correct authority:
   - approver against an active user and system approval permission;
   - case reference against an existing case the requester may view;
   - record reference against the selected downstream system.
5. Reject truncated values such as `MGR-10` when the source says `MGR-104`.
6. Route no match, multiple matches, evidence mismatch, or permission mismatch
   to `NEEDS_REVIEW`.
7. Record the proposed value, resolved value, rule code, and reason in
   `validation_runs`.

## Multi-Part Request Protection

The original subject and message remain the retrieval and review source. A
model-generated summary or `policy_question` may improve readability, but it
cannot replace the original text. Policy retrieval uses the original request
plus an optional generated search query so a shortened proposal cannot silently
drop 1 part of a question.

## Transaction and Concurrency Rules

- Case creation, its 1st audit event, and its initial `WORKFLOW_START` outbox
  message commit in 1 database transaction.
- A requester receipt is a separate `REQUESTER_NOTIFICATION`; it never doubles
  as the durable workflow-start intent.
- A state-changing operation locks the case row and checks `version` before
  applying an allowed transition.
- A successful transition increments `version` and appends exactly 1
  `case_events` row.
- The accepted workflow-start handoff checks for an existing matching
  `ANALYSIS_STARTED` event before rejecting a replay on version. A fresh
  `RECEIVED` to `ANALYZING` transition increments the case version and appends
  that event in 1 transaction.
- n8n never writes the primary database directly. It requests the transition
  through the authenticated primary application boundary defined in
  `docs/WORKFLOW_START_CONTRACT.md`.
- Policy retrieval reuses append-only case events for its durable claim and
  bounded terminal evidence. Exact replay and concurrency checks therefore add
  no retrieval table; the behavior is defined in
  `docs/POLICY_RETRIEVAL_CONTRACT.md`. Its 6/6 application groups and corrected
  cleanup-only verification are verified.
- Human-decision commands add no table. A case-row lock serializes same-case
  commands; `case_events.event_payload` stores the case-scoped command ID,
  canonical input hash, action, and result version. Requester information is a
  bounded event payload, service-agent accepted values update `case_details`,
  and approver decisions update `approvals`. The related case version and 1
  user-attributed event commit atomically. The verified behavior is defined in
  `docs/HUMAN_DECISION_CONTRACT.md`; its 6/6 controlled application groups and
  cleanup are verified.
- Migration `008_human_decision_resume.sql` adds no table. It extends only the
  outbox message-type constraint with `HUMAN_DECISION_RESUME`. The verified
  worker derives this immutable intent from the verified user event, while a
  successful local n8n handoff appends a same-state
  `HUMAN_DECISION_RESUME_ACKNOWLEDGED` case event. Its controlled runtime and
  all 3 bounded route-consumer families are verified through their focused
  contracts. The exact handoff is defined in `docs/HUMAN_RESUME_CONTRACT.md`.
- The verified approved-action materializer reuses `cases`, `case_details`,
  `approvals`, `case_events`, `outbox_messages`, and `delivery_attempts`. The
  immutable downstream payload is created only from a verified current
  approval chain. A later terminal delivery reconciliation increments the case
  version and appends exactly 1 completion or failure event in the same
  transaction. No primary schema change is required; the exact rules are in
  `docs/APPROVED_ACTION_CONTRACT.md`.
- An exact idempotent replay returns the existing case without another AI call,
  approval, outbox message, or downstream record.
- A possible content duplicate uses review rather than a uniqueness constraint
  because 2 people may legitimately submit similar requests.

## Implementation Order

1. Identity and reference tables: `users`, `user_roles`, `managed_systems`, and
   `system_permissions`.
2. Case foundation: `cases`, `case_details`, and `case_events`.
3. AI and decisions: `ai_analysis_runs`, `validation_runs`, and `approvals`.
4. Policy retrieval: `policy_documents` and `policy_chunks` after the embedding
   model is verified locally.
5. Reliable delivery: `outbox_messages`, `delivery_attempts`, and the Service
   Desk Sandbox tables.

Each stage receives its own migration and tests. This keeps the first major AI
Automation project explainable while preserving the final end-to-end design.

The verified Stage 5 migration predates the accepted `WORKFLOW_START` decision
and still permits only downstream actions and requester notifications.
Migration `006_intake_execution.sql` implements the additive change and passed
the user-run primary intake integration check on 2026-08-17. The earlier Stage
5 runtime evidence alone must not be presented as intake evidence.
The accepted detailed intake behavior is defined in
`docs/INTAKE_CONTRACT.md`.

Migration `007_ai_analysis_runtime.sql` additively aligns the verified Stage 3
analysis table with the accepted AI-analysis lifecycle. It retains the earlier
migration as historical evidence and adds bounded attempt numbering, terminal
timestamps, lifecycle statuses, time consistency, and exact attempt identity.
Its focused user-run disposable database check passed on 2026-08-17, including
the lifecycle constraints, terminal analysis-failure evidence, bounded
attempts, zero-model-call `SKIPPED` outcome, and cleanup.
